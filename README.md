# Requirements Review

Skill для Claude, який перевіряє вимоги (requirements) на якість **перед** тест-аналізом — до того, як тестувальник почне писати тест-кейси.

Мета — знайти конкретні, обґрунтовані проблеми в тексті вимоги (а не абстрактну критику типу «вимога погана»), спираючись виключно на те, що реально написано в тексті.

## Що вміє skill

Перевіряє вимогу за **7 критеріями якості**:

| # | Критерій | Що шукає |
|---|----------|----------|
| 1 | Атомарність | Чи вимога описує рівно одну поведінку/правило (без «і», «а також», кількох умов в одному пункті) |
| 2 | Однозначність | Слова без чіткого значення: «швидко», «зручно», «коректно», «інтуїтивно» тощо — без конкретних порогів |
| 3 | Повнота | Чи описані негативні сценарії та межові значення (пусті поля, мін/макс, ліміти) |
| 4 | Несуперечність | Внутрішні протиріччя або протиріччя з іншими наданими вимогами |
| 5 | Неповторюваність | Дублювання (повне чи часткове) з іншою наданою вимогою |
| 6 | Тестованість | Чи можна до кожного твердження написати конкретну перевірку з очікуваним результатом |
| 7 | Реалізовність | Ознаки технічної нереалізовності прямо в тексті вимоги |

Для кожної знахідки skill завжди дає **три поля**: критерій → точна цитата з тексту → пояснення проблеми. Без цитати — це не знахідка. Прогалини (те, чого в тексті бракує) оформлюються не як твердження «система не працює», а як **питання до BA**.

Наприкінці — підсумок: чи вимога готова / умовно готова / не готова до тест-аналізу.

**Skill свідомо НЕ робить:**
- не переписує вимогу за автора (якщо окремо не попросити);
- не оцінює орфографію/форматування;
- не позначає як проблему звичайну практику чи розумне замовчування.

## Як підключити

1. Покладіть файл `SKILL.md` за шляхом:
   ```
   /mnt/skills/user/requirements-review/SKILL.md
   ```
2. Claude автоматично підхоплює skill із теки `/mnt/skills/user/` — окремої активації не потрібно.
3. Skill спрацьовує сам, коли ви:
   - просите перевірити/зробити рев'ю вимоги;
   - питаєте «чи готова ця вимога до тестування»;
   - просите знайти проблеми у вимозі перед написанням тест-кейсів.

   Слово «рев'ю» вживати необов'язково — достатньо смислового запиту.

## Приклад «до / після»

### До (вихідна вимога)

> **REQ-042.** Система повинна швидко обробляти запити користувача на скидання пароля і надсилати сповіщення, а також логувати всі дії адміністратора.

### Після (звіт skill'а)

```
## Рев'ю вимоги: REQ-042

### Знахідки

1. **Критерій:** Атомарність
   **Цитата:** «обробляти запити... на скидання пароля і надсилати сповіщення,
   а також логувати всі дії адміністратора»
   **Проблема:** в одному пункті об'єднано три різні поведінки (скидання
   пароля, сповіщення, логування дій адміністратора) — це три окремі
   вимоги, склеєні в одну.

2. **Критерій:** Однозначність
   **Цитата:** «повинна швидко обробляти»
   **Проблема:** немає визначення порогу («швидко» — це скільки секунд/мс?),
   тому за цим твердженням не можна написати тест.

3. **Критерій:** Тестованість
   **Цитата:** «швидко обробляти запити»
   **Проблема:** суб'єктивна оцінка без метрики — неможливо звести до
   перевірюваного факту без уточнення порогу.

### Питання до BA

- Який конкретно час обробки запиту вважається «швидким» (у секундах/мс)?
- Що має відбутися, якщо користувач надішле кілька запитів на скидання
  пароля поспіль (rate limiting)?
- Яким має бути формат і канал сповіщення (email/SMS/push)?
- Чи стосується логування дій адміністратора лише скидання паролів, чи
  всіх дій адміністратора в системі взагалі?

### Висновок

Вимога **не готова** до тест-аналізу: критична проблема — відсутність
атомарності (три різні поведінки в одному пункті) ускладнює написання
тест-кейсів і відстеження покриття. Некритична, але важлива — відсутність
порогу для «швидко» унеможливлює тест продуктивності без додаткового
уточнення.
```

Бачите різницю: замість «вимога погана» — конкретні цитати, прив'язані до критеріїв, і чіткі питання до BA замість здогадок.
